The Problem

NDB Cluster has no native RANGE partitioning. Hash-based distribution means every scan touches all fragments — even when data is naturally time-ordered.
  • Time-series data is the most common use case for range partitioning
  • Without it, you cannot efficiently expire old data — DELETE is row-by-row
  • Scans on time-bounded queries hit every data node regardless of time range
  • MySQL's generic partitioning layer adds overhead and doesn't integrate with NDB's kernel
  • No way to DROP PARTITION for instant data removal of old time windows

The Solution: Server-Side Range Resolution

A new RANGE_PARTITION fragment type in DBDIH that performs binary search on a Range2FragmentMap structure, routing operations to the correct fragment without any hash computation for partition selection.

Key Design Decisions

  • Range boundaries stored in a contiguous memory block alongside fragment IDs
  • Partition key extracted in DBTC, passed to DBDIH via pointer in EXECUTE_DIRECT signal
  • Binary search with type-aware native comparison (not memcmp)
  • Full tuple hash still computed for LQH/DBACC distribution within fragments
  • RCU-safe map swap for online ADD/DROP PARTITION

Single Allocation

Header + fragment IDs + boundaries in one contiguous block via lc_ndbd_pool_malloc. Cache-friendly binary search. Max ~82 KB for 8,160 partitions.

Type-Aware Comparison

Boundaries stored in native endian format. range_compare() casts to Int32, Int64, etc. based on m_boundary_type. Not memcmp — correct on little-endian (x86/ARM).

DROP PARTITION: Instant Data Expiry

DROP PARTITION is O(1) — removes the first (oldest) partition by deallocating the fragment. No row-by-row DELETE. Millions of rows removed in milliseconds.

How It Works

P0: < 2024
P1: 2024
P2: 2025
P3: 2026

After DROP PARTITION p0: 3 partitions remain

P1: 2024
P2: 2025
P3: 2026
(freed)

After ADD PARTITION p4: sliding window

P1: 2024
P2: 2025
P3: 2026
P4: 2027
  • Lower bound enforcement — inserts below the dropped boundary are rejected
  • RCU-safe swap — concurrent operations see consistent range map via NdbSeqLock
  • Online operation — uses ALGORITHM=INPLACE, no table copy

Key Innovation: fragId / fragNo Separation

Before (Hash Partitioning)

  • fragId = fragNo (always equal)
  • Fragment 0 is always the first fragment
  • Fragments are never removed
  • No concept of "real" vs "logical" ID

After (Range Partitioning)

  • fragId = permanent identifier (inter-block)
  • fragNo = position in current array (0..N-1)
  • After DROP: fragNo 0 may be fragId 3
  • m_startFid_offset tracks the delta

This separation required auditing and fixing every use of fragment identifiers across DBDIH, DBLQH, SUMA, TRIX, DBTUX, Backup, and LCP signals. Phases 3–8 were dedicated to getting this right — the single hardest part of the implementation.

// The fundamental conversion
fragNo = fragId - tabPtr.p->m_startFid_offset;   // real → array index
fragId = fragNo + tabPtr.p->m_startFid_offset;   // array index → real

// After dropping partition 0, then 1:
// m_startFid_offset = 2
// fragNo=0 → fragId=2, fragNo=1 → fragId=3, ...

Partition columns must be part of the primary key. The RANGE COLUMNS syntax is used (not RANGE(expr)), ensuring the raw column value is available for binary search without expression evaluation.

SQL Usage Examples

-- Create a time-partitioned table
CREATE TABLE events (
    event_id   BIGINT NOT NULL,
    event_date DATE   NOT NULL,
    payload    VARCHAR(1000),
    PRIMARY KEY (event_id, event_date)
) ENGINE=NDB
PARTITION BY RANGE COLUMNS (event_date) (
    PARTITION p2024 VALUES LESS THAN ('2025-01-01'),
    PARTITION p2025 VALUES LESS THAN ('2026-01-01'),
    PARTITION p2026 VALUES LESS THAN ('2027-01-01'),
    PARTITION p2027 VALUES LESS THAN ('2028-01-01')
);

-- Insert data — routed to correct partition automatically
INSERT INTO events VALUES (1, '2025-06-15', 'data...');

-- Drop oldest partition — instant, O(1)
ALTER TABLE events DROP PARTITION p2024
    ALGORITHM=INPLACE;

-- Add new partition for next year
ALTER TABLE events ADD PARTITION (
    PARTITION p2028 VALUES LESS THAN ('2029-01-01')
);

-- Scan pruning: only touches relevant partitions
SELECT * FROM events
WHERE event_date BETWEEN '2025-01-01' AND '2025-12-31';

Time Window Data in RonDB

Range partitioning transforms RonDB into a time-window data store: new partitions appear as time advances, old partitions vanish when data expires — with zero row-level overhead.

IoT / Telemetry

Sensor data partitioned by day or hour. Drop yesterday's high-frequency data, keep weekly summaries. Scan pruning limits queries to the relevant time slice.

Financial Trading

Tick data partitioned by trading day. End-of-day: DROP PARTITION to archive, ADD PARTITION for tomorrow. PK lookups route directly to the correct day's fragment.

Log / Event Storage

Application logs with a 30-day retention window. Monthly partitions with automated DROP of the oldest. No costly DELETE FROM ... WHERE ts < cutoff.

Session / Cache Data

User sessions partitioned by epoch ranges. Expired sessions removed in bulk via partition drop. Active sessions accessed via PK lookup at full NDB speed.

Impact: Scan Pruning

Without Range Partitioning

Hash distribution scatters time-ordered data across all fragments. Every query must scan everything.

With Range Partitioning

Range-partitioned queries only touch the fragments that contain matching data. Binary search identifies them.

Current Limitations

  • ⚠
    DROP only the first (oldest) partition
    By design: maintains contiguous fragment ID space. Matches the sliding-window use case where you always remove the oldest data.
  • ⚠
    ADD only at the end (highest boundary)
    New partitions must have boundaries greater than all existing ones. Consistent with MySQL RANGE semantics.
  • ⚠
    Fixed-size column types only (Tier 1)
    INT, BIGINT, DATE, DATETIME, TIMESTAMP. VARCHAR and multi-column composite keys require Tier 2 B-tree implementation (planned).
  • ⚠
    Not compatible with FULLY_REPLICATED tables
    Explicitly rejected at CREATE TABLE time. Range partitioning and full replication have conflicting distribution models.
  • ⚠
    No client-side transaction hinting yet
    startTransaction() does not yet use range resolution for optimal TC node selection. Planned for a future phase.
  • ⚠
    Partition column must be in the primary key
    Required so that partition key is available during PK operations for range lookup. Standard MySQL partition requirement.

Restart Persistence

Range maps and the m_startFid_offset are persisted on disk and fully restored during node restart and system restart. Data survives cluster restarts without any re-creation.

What Gets Persisted

  • Range2FragmentMap structure (boundaries + frag IDs)
  • m_startFid_offset (tracks dropped partitions)
  • Boundary type metadata
  • Fragment count and mapping

Restore Flow

  • DBDICT restores table metadata on restart
  • Range map allocated and populated in prepare_add_table
  • DBDIH receives map pointer via DiAddTabReq
  • Verified by ndb_partition_range_restart test
-- Test scenario: create, insert, restart, verify
CREATE TABLE t_restart (...) PARTITION BY RANGE COLUMNS (d) (...);
INSERT INTO t_restart VALUES (...);   -- data across partitions
ALTER TABLE t_restart DROP PARTITION p0;
-- Restart all nodes
-- After restart: range map, offset, and data all intact
SELECT * FROM t_restart;              -- returns surviving rows
INSERT INTO t_restart VALUES (...);   -- routes correctly
