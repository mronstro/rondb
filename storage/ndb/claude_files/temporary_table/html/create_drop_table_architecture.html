1. Overview: Block Roles

NDB Cluster uses a distributed block architecture where each functional unit (block) handles a specific aspect of the system. Table creation and dropping involves six main blocks:

Block interaction during CREATE TABLE. DBDICT orchestrates, DBDIH distributes fragments, DBLQH manages local fragments with DBTUP/DBACC storage, DBTC/DBSPJ learn about new tables.
BlockRole in CREATE/DROP TABLE
DBDICTSchema manager and DDL orchestrator. Owns the SchemaTransaction framework. Coordinates all other blocks via SCHEMA_TRANS_IMPL_REQ broadcasts. Writes schema files to disk. One instance per node, with one elected as master.
DBDIHDistribution handler. Manages fragment-to-node assignment, replica placement, and fragment metadata. DBTC uses DBDIH to route operations to the correct DBLQH instance. Persists table/fragment data to disk.
DBLQHLocal query handler. One instance per LDM thread (via DblqhProxy). Creates local fragment storage by coordinating DBTUP (tuples) and DBACC (hash index). Manages redo logging and LCP for fragments.
DBTUPTuple storage manager. Allocates and manages row storage (fixed + variable-length parts). Creates fragment-level storage structures.
DBACCHash index manager. Creates and manages the hash index structure used for primary key lookups on each fragment.
DBTC / DBSPJTransaction coordinator and pushed-join coordinator. Need to know about tables to route operations. Maintain TableRecord with enabled/dropping flags.

2. SchemaTransaction Framework

All DDL operations in NDB run within a SchemaTransaction coordinated by the DBDICT master. The master sends SCHEMA_TRANS_IMPL_REQ signals to all DBDICT instances (including itself) to drive each phase. This provides distributed atomicity: either all nodes complete the DDL or all abort.

2.2 Request Types (RT_)

The requestInfo field of SCHEMA_TRANS_IMPL_REQ carries the request type (SchemaTransImpl.hpp:34-46):

RT_ ValueHexTrans StateSchema File Write?Purpose
RT_START0x0 TS_STARTINGNo Allocate SchemaTrans on all nodes. Set m_isMaster flag.
RT_PARSE0x1 TS_PARSINGNo Execute operation-specific parse handler on all nodes. Carries gsn of the DDL signal (e.g., GSN_CREATE_TABLE_REQ) and serialized table definition.
RT_FLUSH_PREPARE0x2 TS_FLUSH_PREPAREConditional If m_flush_prepare: write schema file with operation state. Synchronize all nodes before entering PREPARE.
RT_PREPARE0x3 TS_PREPARINGNo Execute operation-specific prepare handler. This is where the heavy work happens (DBLQH fragment creation, DBDIH distribution).
RT_FLUSH_COMMIT0x6 TS_FLUSH_COMMITConditional If m_flush_commit: write schema file. Acquire commit mutex. Synchronize before commit.
RT_COMMIT0x7 TS_COMMITTINGNo Execute operation-specific commit handler. Sent to slaves first, master last (ensures slaves see commit before master completes).
RT_FLUSH_COMPLETE0x8 TS_FLUSH_COMPLETEConditional If m_flush_complete: write schema file. Release commit mutex.
RT_COMPLETE0x9 TS_COMPLETINGNo Execute operation-specific complete handler. Usually no-op for CREATE TABLE.
RT_END0xa TS_ENDINGConditional Write final schema file state. Release SchemaTrans on all nodes. Release schema lock.
RT_ABORT_PARSE0x4 TS_ABORTING_PARSENo Rollback parse phase. Called on error during PARSE.
RT_ABORT_PREPARE0x5 TS_ABORTING_PREPARENo Rollback prepare phase. Called on error during PREPARE.

2.3 FLUSH Phases & Schema File Writes

The three FLUSH phases (FLUSH_PREPARE, FLUSH_COMMIT, FLUSH_COMPLETE) exist to persist the schema transaction state to disk before entering the next phase. This ensures crash recovery: if a node crashes mid-DDL, the schema file records which phase was reached, allowing recovery to either complete or abort the operation.

When are schema files written? Each FLUSH phase checks a flag (m_flush_prepare, m_flush_commit, m_flush_complete). If set, the slave calls trans_log() followed by startWriteSchemaFile() (Dbdict.cpp:30433-30475). The CONF reply is sent only after the disk write completes (callback: slave_writeSchema_conf()). If the flag is not set, the slave skips the write and replies immediately.
Commit mutex: During RT_FLUSH_COMMIT, each node acquires a commit mutex (m_commit_mutex) that serializes commit phases across concurrent schema transactions. This mutex is held until RT_FLUSH_COMPLETE releases it. For temporary tables, this serialization may be unnecessary.

2.4 Master-Slave Coordination

DBDICT Master (node with c_masterNodeId):
  • Controls the state machine, drives phase transitions
  • Sends SCHEMA_TRANS_IMPL_REQ to all alive nodes (including self)
  • Uses SafeCounter to track CONF replies from each node
  • Calls trans_recv_reply() when all nodes have replied
  • Only proceeds to next phase when ALL nodes confirm current phase
  • Holds the global schema lock (dict_lock_trylock()) for entire transaction

DBDICT Slaves (all other nodes):
  • Maintain local SchemaTrans copy with m_isMaster = false
  • Execute operation handlers when master sends RT_PARSE/PREPARE/COMMIT/COMPLETE
  • Each handler runs independently on local data (DBLQH, DBDIH on same node)
  • Schema file writes happen locally during FLUSH phases
  • Reply with SCHEMA_TRANS_IMPL_CONF (or REF on error)

Key invariant: The master never advances to the next phase until ALL nodes
have confirmed the current phase. This is what provides distributed atomicity.

2.5 NDB API Side

From the NDB API perspective (NdbDictionaryImpl.cpp), a CREATE TABLE involves three API calls that map to the schema transaction phases:

NdbDictInterface::beginSchemaTrans()   (line 9972)
  → GSN_SCHEMA_TRANS_BEGIN_REQ → DBDICT
  → triggers RT_START broadcast
  ← SCHEMA_TRANS_BEGIN_CONF (with transId, transKey)

NdbDictInterface::sendCreateTable()    (line 4977)
  → GSN_CREATE_TABLE_REQ (with serialized table descriptor)
  → triggers RT_PARSE broadcast
  ← CREATE_TABLE_CONF (with tableId, tableVersion)

NdbDictInterface::endSchemaTrans()     (line 10018)
  → GSN_SCHEMA_TRANS_END_REQ (flags=Commit)
  → triggers the full phase sequence:
     RT_FLUSH_PREPARE → RT_PREPARE → RT_FLUSH_COMMIT → RT_COMMIT
     → RT_FLUSH_COMPLETE → RT_COMPLETE → WAIT_GCP → RT_END
  ← SCHEMA_TRANS_END_CONF
The endSchemaTrans(Commit) call triggers 7 broadcast rounds plus WAIT_GCP. This is where most of the latency lives.

3. CREATE TABLE: Complete Signal Flow

Below is the complete end-to-end signal flow for CREATE TABLE, showing exactly where each SCHEMA_TRANS_IMPL_REQ phase wraps the actual DDL work. Each phase band shows what happens on every node when the master broadcasts that phase.

3.1 RT_START Begin Transaction

NDB API → SCHEMA_TRANS_BEGIN_REQ → DBDICT master
  │
  ├─ dict_lock_trylock() — acquire global schema lock (blocks other DDL)
  ├─ Allocate SchemaTrans (state = TS_STARTING)
  │
  ├─ SCHEMA_TRANS_IMPL_REQ(RT_START) → all nodes
  │     Each slave: allocate local SchemaTrans, m_isMaster=false
  │     Each slave → SCHEMA_TRANS_IMPL_CONF
  │
  └─ SCHEMA_TRANS_BEGIN_CONF → NDB API
       State: TS_STARTED

3.2 RT_PARSE Parse & Validate

NDB API → CREATE_TABLE_REQ → DBDICT master
  │
  ├─ handleClientReq(): allocate SchemaOp + CreateTableRec
  │
  ├─ Master-only parse work:
  │     CREATE_FRAGMENTATION_REQ → DBDIH  (calculate fragment distribution)
  │     DBDIH → CREATE_FRAGMENTATION_CONF   (returns fragment list, NO side effects)
  │     getFreeObjId() — scan schema file for free table ID
  │     seizeTableRecord() — allocate TableRecord + DictObject
  │     handleTabInfoInit() — populate metadata from DICTTABINFO
  │     Build KeyDescriptor
  │
  ├─ SCHEMA_TRANS_IMPL_REQ(RT_PARSE) → all nodes
  │     Contains: gsn=GSN_CREATE_TABLE_REQ + serialized table definition
  │     Each node: slave_run_parse() → createTable_parse()
  │       • Allocate local SchemaOp + CreateTableRec
  │       • seizeTableRecord(), handleTabInfoInit()
  │       • Build local KeyDescriptor
  │       • BUG: TR_Temporary bit NOT set (#ifdef DOES_NOT_WORK_CURRENTLY)
  │     Each node → SCHEMA_TRANS_IMPL_CONF
  │
  └─ CREATE_TABLE_CONF → NDB API (with tableId, tableVersion)
       State: TS_STARTED, OS_PARSED

At this point the NDB API has the table ID but the table is not yet usable. The API now calls endSchemaTrans(Commit) which triggers the remaining phases:

3.3 RT_FLUSH_PREPARE Synchronize Before Prepare

NDB API → SCHEMA_TRANS_END_REQ(Commit) → DBDICT master
  │
  ├─ trans_prepare_start()
  │
  ├─ SCHEMA_TRANS_IMPL_REQ(RT_FLUSH_PREPARE) → all nodes
  │     Each node: slave_run_flush()
  │       • State: TS_STARTED → TS_FLUSH_PREPARE
  │       • trans_log() — log operation state
  │       • if m_flush_prepare: startWriteSchemaFile() [DISK I/O]
  │       •   slave_writeSchema_conf() callback after write completes
  │       • else: skip write, reply immediately
  │     Each node → SCHEMA_TRANS_IMPL_CONF
  │
  └─ trans_prepare_first() — begin iterating operations
       State: TS_FLUSH_PREPARE → TS_PREPARING

3.4 RT_PREPARE Create Table in DBLQH & DBDIH

This is the heaviest phase. The master sends RT_PREPARE to all nodes, and each node independently runs createTable_prepare() which orchestrates fragment creation locally.

SCHEMA_TRANS_IMPL_REQ(RT_PREPARE) → all nodes

On each node, createTable_prepare() executes this sequence:

Step 1: Write table descriptor to disk
  ├─ savetodisk = !(m_bits & TR_Temporary)
  ├─ if savetodisk: writeTableFile() [DISK I/O]
  └─ else (temp table): skip directly to callback

Step 2: Create table structure in DBLQH
  ├─ createTab_local() → CREATE_TAB_REQ → DBLQH (via DblqhProxy → all LDM instances)
  │     DBLQH: allocate Tablerec, status = ADD_TABLE_ONGOING
  │     DBLQH → CREATE_TAB_REQ → DBTUP (create table-level storage)
  │     (For ordered indexes: also sends to DBTUX)
  │     DBTUP → CREATE_TAB_CONF → DBLQH
  └─ DBLQH → CREATE_TAB_CONF → DBDICT

Step 3: Add attributes to DBLQH
  ├─ sendLQHADDATTRREQ(): batched attribute definitions
  │     LQHADDATTREQ → DBLQH (via DblqhProxy → all LDM instances)
  │     DBLQH: forwards to DBTUP + DBTUX for attribute metadata
  └─ DBLQH → LQHADDATTCONF → DBDICT

Step 4: Register table in DBDIH
  ├─ createTab_dih() → DIADDTABREQ → DBDIH (with fragmentation section)
  │     DBDIH: prepare_add_table() — allocate TabRecord, set metadata
  │     DBDIH: allocFragments() — seize Fragmentstore records
  │     DBDIH: allocStoredReplica() — for each replica per fragment
  │     DBDIH: CONTINUEB(ZPACK_TABLE_INTO_PAGES) — serialize to pages [DISK I/O]
  │     DBDIH: initTableFile(), write table file to disk [DISK I/O]
  │
  │     For each local fragment (fragment loop):
  │     DBDIH → ADD_FRAGREQ → DBDICT → LQHFRAGREQ → DBLQH
  │       DBLQH: insertFragrec() — seize Fragrecord from pool
  │       DBLQH: initFragrec():
  │           if tempTable: logFlag=STATE_FALSE, lcpFlag=LCP_STATE_FALSE
  │       DBLQH → ACCFRAGREQ → DBACC (create hash index fragment)
  │       DBACC → ACCFRAGCONF → DBLQH
  │       DBLQH → TUPFRAGREQ → DBTUP (create tuple storage fragment)
  │       DBTUP → TUPFRAGCONF → DBLQH
  │       DBLQH → LQHFRAGCONF → DBDICT → ADD_FRAGCONF → DBDIH
  │       (DBDIH calls sendAddFragreq() recursively for next fragment)
  │
  └─ DBDIH → DIADDTABCONF → DBDICT

Step 5: Local commit to DBLQH
  ├─ TAB_COMMITREQ → DBLQH (via DblqhProxy → all LDM instances)
  │     DBLQH: set tableStatus = TABLE_DEFINED
  └─ DBLQH → TAB_COMMITCONF → DBDICT

Each node → SCHEMA_TRANS_IMPL_CONF → master
State: OS_PREPARING → OS_PREPARED
PREPARE phase on each node: 5 sequential steps with N fragment-creation loops. Each fragment requires a 3-hop routing: DBDIH → DBDICT → DBLQH and back.
Signal count in PREPARE (per node): CREATE_TAB_REQ (1) + LQHADDATTREQ (1-2 batches) + DIADDTABREQ (1) + per-fragment: ADD_FRAGREQ + LQHFRAGREQ + ACCFRAGREQ + TUPFRAGREQ (4 × N) + TAB_COMMITREQ (1). For a table with 8 fragments on 2 nodes (4 local): ~3 + 4×4 = 19 signals per node, each fanned through DblqhProxy to all LDM instances.

3.5 RT_FLUSH_COMMIT Synchronize Before Commit

SCHEMA_TRANS_IMPL_REQ(RT_FLUSH_COMMIT) → all nodes
  Each node: slave_run_flush()
    • State: TS_PREPARING → TS_FLUSH_COMMIT
    • trans_log()
    • if m_flush_commit: startWriteSchemaFile() [DISK I/O]
    • slave_writeSchema_conf():
        Acquire commit mutex (m_commit_mutex)
        State → TS_COMMITTING
  Each node → SCHEMA_TRANS_IMPL_CONF

Master: trans_commit_first()
  • Acquire commit mutex (may wait for GCI)
  • Callback: trans_commit_mutex_locked()
  • State: TS_FLUSH_COMMIT → TS_COMMITTING

3.6 RT_COMMIT Activate Table in DBTC, DBSPJ, DBDIH

SCHEMA_TRANS_IMPL_REQ(RT_COMMIT) → slaves first, then master

On each node, createTable_commit() executes:

Step 1: Database tracking
  ├─ createTab_activate() → CONNECT_TABLE_DB_REQ → DBLQH + DBTC
  │     Register table in database quota tracking

Step 2: Activate in DBDIH
  ├─ TAB_COMMITREQ → DBDIH
  │     DBDIH: tabStatus = TS_ACTIVE — table now routable by DBTC

Step 3: Activate in DBSPJ
  ├─ TC_SCHVERREQ → DBSPJ (schema version notification)
  ├─ TAB_COMMITREQ → DBSPJ
  │     DBSPJ: enabled = true

Step 4: Activate in DBTC
  ├─ TAB_COMMITREQ → DBTC
  │     DBTC: enabled = true — table now accepts transactions

Step 5: Notify replication
  └─ CREATE_TAB_CONF → SUMA
       SUMA distributes to replication subscribers

Each node → SCHEMA_TRANS_IMPL_CONF → master
State: OS_COMMITTING → OS_COMMITTED

3.7 RT_FLUSH_COMPLETE Synchronize After Commit

SCHEMA_TRANS_IMPL_REQ(RT_FLUSH_COMPLETE) → all nodes
  Each node: slave_run_flush()
    • State: TS_COMMITTING → TS_FLUSH_COMPLETE
    • trans_log()
    • if m_flush_complete: startWriteSchemaFile() [DISK I/O]
    • slave_writeSchema_conf():
        Release commit mutex (m_commit_mutex)
        State → TS_COMPLETING
  Each node → SCHEMA_TRANS_IMPL_CONF

3.8 RT_COMPLETE Finalize

SCHEMA_TRANS_IMPL_REQ(RT_COMPLETE) → all nodes

  Each node: createTable_complete()
    • No-op for CREATE TABLE — just confirms
  Each node → SCHEMA_TRANS_IMPL_CONF

State: OS_COMPLETING → OS_COMPLETED

3.9 WAIT_GCP + RT_END Transaction Cleanup

After all operations complete, the master finalizes the transaction:

Optional GCP wait:
  if m_wait_gcp_on_commit:
    WAIT_GCP_REQ → DBDIH
    Wait for Global Checkpoint boundary (up to ~2 seconds)
    Ensures committed schema change is durable even if all nodes crash
    DBDIH → WAIT_GCP_CONF

SCHEMA_TRANS_IMPL_REQ(RT_END) → all nodes
  Each node: slave_run_flush() for RT_END
    • State: TS_COMPLETING → TS_ENDING
    • trans_log()
    • Write final schema file state [DISK I/O]
    • sendTransConfRelease() — release local SchemaTrans
  Each node → SCHEMA_TRANS_IMPL_CONF

Master: trans_end_recv_reply()
  • dict_lock_unlock() — release global schema lock
  • SCHEMA_TRANS_END_CONF → NDB API
  • Release SchemaTrans object
Total CREATE TABLE cost:
  • 11 SCHEMA_TRANS_IMPL_REQ broadcast rounds (START, PARSE, FLUSH_PREPARE, PREPARE, FLUSH_COMMIT, COMMIT, FLUSH_COMPLETE, COMPLETE, END) — each is a round-trip to all N nodes
  • Up to 4 schema file writes (FLUSH_PREPARE, FLUSH_COMMIT, FLUSH_COMPLETE, END) — disk I/O on every node
  • PREPARE phase internal signals: ~19 signals per node for an 8-fragment table
  • COMMIT phase internal signals: ~6 signals per node (DBTC, DBSPJ, DBDIH, SUMA)
  • WAIT_GCP: up to ~2 seconds
  • Commit mutex: serialization with concurrent DDL

4. DROP TABLE: Complete Signal Flow

DROP TABLE follows the same SchemaTransaction phases. The DDL-specific work is distributed differently across phases compared to CREATE TABLE.

4.1 BEGIN + RT_PARSE Parse & Validate

(BEGIN: same as CREATE TABLE — RT_START broadcast, alloc SchemaTrans)

NDB API → DROP_TABLE_REQ → DBDICT master

SCHEMA_TRANS_IMPL_REQ(RT_PARSE) → all nodes
  Each node: dropTable_parse()
    • Validate tableId and version match
    • Check m_read_locked (not locked for backup)
    • Log schema operation as SF_DROP in schema file
    • Sets up sub-operations (drop triggers, remove from index list)
  Each node → SCHEMA_TRANS_IMPL_CONF

DROP_TABLE_CONF → NDB API

4.2 RT_FLUSH_PREPARE + RT_PREPARE

SCHEMA_TRANS_IMPL_REQ(RT_FLUSH_PREPARE) → all nodes
  Schema file write (conditional)

SCHEMA_TRANS_IMPL_REQ(RT_PREPARE) → all nodes
  Each node: dropTable_prepare()
    • Acquire backup mutex — prevents concurrent backup reading this table
    • dropTable_backup_mutex_locked():
        Verify table still not locked for backup
    • Release mutex, confirm prepare
  Each node → SCHEMA_TRANS_IMPL_CONF

4.3 RT_FLUSH_COMMIT + RT_COMMIT Sequential Block Drop

COMMIT is where the actual drop coordination happens. Blocks are notified sequentially with PREP_DROP_TAB_REQ:

SCHEMA_TRANS_IMPL_REQ(RT_FLUSH_COMMIT) → all nodes
  Schema file write + acquire commit mutex

SCHEMA_TRANS_IMPL_REQ(RT_COMMIT) → slaves first, master last

On each node, dropTable_commit() executes:

  ├─ Remove index from base table's index list (if index)
  ├─ Send event NDB_LE_DropSchemaObject
  │
  ├─ dropTable_commit_nextStep() — SEQUENTIAL block iteration:
  │
  │  Step 1: PREP_DROP_TAB_REQ → DBLQH (via DblqhProxy, all LDM instances)
  │     DBLQH: mark table dropping, wait for active operations to drain
  │     DBLQH → PREP_DROP_TAB_CONF → DBDICT
  │     ↓ wait for CONF before sending next ↓
  │
  │  Step 2: PREP_DROP_TAB_REQ → DBSPJ
  │     DBSPJ: mark table dropping
  │     DBSPJ → PREP_DROP_TAB_CONF → DBDICT
  │
  │  Step 3: PREP_DROP_TAB_REQ → DBTC
  │     DBTC: mark table dropping, reject new transactions
  │     DBTC → PREP_DROP_TAB_CONF → DBDICT
  │
  │  Step 4: PREP_DROP_TAB_REQ → DBDIH
  │     DBDIH: tabStatus = TS_DROPPING
  │     DBDIH → PREP_DROP_TAB_CONF → DBDICT
  │
  └─ dropTable_commit_done()

Each node → SCHEMA_TRANS_IMPL_CONF → master
COMMIT phase sends PREP_DROP_TAB_REQ sequentially. The order DBLQH → DBSPJ → DBTC → DBDIH ensures in-flight DBLQH operations complete before DBTC stops accepting new ones.

4.4 RT_FLUSH_COMPLETE + RT_COMPLETE Resource Deallocation

COMPLETE is where actual resources are freed. Again sequential block processing:

SCHEMA_TRANS_IMPL_REQ(RT_FLUSH_COMPLETE) → all nodes
  Schema file write + release commit mutex

SCHEMA_TRANS_IMPL_REQ(RT_COMPLETE) → all nodes

On each node, dropTable_complete() executes:

  ├─ dropTable_complete_nextStep() — SEQUENTIAL block iteration:
  │
  │  Step 1: DROP_TAB_REQ → DBTC
  │     DBTC: release TableRecord
  │     DBTC → DROP_TAB_CONF → DBDICT
  │
  │  Step 2: DROP_TAB_REQ → DBSPJ
  │     DBSPJ: release TableRecord
  │     DBSPJ → DROP_TAB_CONF → DBDICT
  │
  │  Step 3: DROP_TAB_REQ → DBLQH (via DblqhProxy)
  │     DBLQH: wait for usage to drain + LCP to finish
  │     DBLQH → DROP_TAB_CONF → DBDICT
  │
  │  Step 4: DROP_TAB_REQ → DBDIH
  │     DBDIH: update m_used_log_parts, remove from LCP queues
  │     DBDIH: wait for I/O completion (tabLcpStatus)
  │     DBDIH: releaseFragments() — free Fragmentstore + ReplicaRecord
  │     DBDIH: delete table file from disk [DISK I/O]
  │     DBDIH → DROP_TAB_CONF → DBDICT
  │
  │  Step 5: DROP_TAB_REQ → DBLQH (release pass, via DblqhProxy)
  │     DBLQH: dropTable_nextStep() state machine:
  │       DROP_TABLE_WAIT_DONE → DROP_TABLE_ACC → DROP_TABLE_TUP → DROP_TABLE_TUX
  │       DROP_TAB_REQ → DBACC (release hash index)
  │       DROP_TAB_REQ → DBTUP (release tuple storage)
  │       DROP_TAB_REQ → DBTUX (if ordered index)
  │     removeTable() — release Fragrecords, free fragrec/fragid arrays
  │     DBLQH → DROP_TAB_CONF → DBDICT
  │
  └─ dropTable_complete_done():
       unlinkDictObject(), releaseTableObject()
       DROP_TAB_CONF → SUMA — replication notification

Each node → SCHEMA_TRANS_IMPL_CONF → master

Then: WAIT_GCP (if applicable) + RT_END (same as CREATE TABLE)
COMPLETE phase: 5 sequential steps. DBLQH is visited twice — first to wait for operations to drain, then to actually release fragment storage via ACC/TUP/TUX.
Total DROP TABLE cost:
  • 11 SCHEMA_TRANS_IMPL_REQ broadcast rounds (same as CREATE)
  • COMMIT phase: 4 sequential PREP_DROP_TAB_REQ round-trips per node
  • COMPLETE phase: 5 sequential DROP_TAB_REQ round-trips per node
  • Total sequential internal signals: 9 round-trips per node (not parallelized)
  • Schema file writes + WAIT_GCP + commit mutex (same overhead as CREATE)

7. Optimization Opportunities

7.1 Generic Optimizations (All Tables)

G1: Parallelize DROP TABLE Block Notifications

Currently PREP_DROP_TAB_REQ is sent sequentially: DBLQH → DBSPJ → DBTC → DBDIH. The sequential ordering ensures DBLQH drains in-flight operations before DBTC stops accepting new ones. However, this can be relaxed: send to all blocks in parallel, then verify drain conditions after all respond.

Similarly, DROP_TAB_REQ in COMPLETE could be partially parallelized.

Impact: Reduces DROP internal signals from 9 sequential to ~3 parallel rounds.
G2: Batch LQHADDATTREQ with CREATE_TAB_REQ

For tables with few attributes, the separate LQHADDATTREQ signal(s) could be combined with the initial CREATE_TAB_REQ to eliminate a round-trip.

Impact: Saves 1 proxy-fanned round-trip per table creation.
G3: Inline DBDIH Table Packing

The ZPACK_TABLE_INTO_PAGES continuation in DBDIH serializes table metadata into pages via deferred signals (CONTINUEB). For simple tables, this could be done inline without the continuation overhead.

Impact: Saves 1-2 continuation signal delays in DBDIH.

7.2 Temporary Table Specific Optimizations

T1: Fix TR_Temporary Bit PREREQUISITE

Remove #ifdef DOES_NOT_WORK_CURRENTLY at Dbdict.cpp:5843 to enable the TR_Temporary bit in TableRecord::m_bits. Investigate why it was disabled. This gates all DBDICT-level optimizations.

Impact: Enables further optimizations. Low risk.
T2: Skip SUMA Notifications

Temporary tables need no replication. Skip CREATE_TAB_CONF to SUMA during createTab_alterComplete() and DROP_TAB_CONF to SUMA during dropTable_complete_done().

Impact: Saves 1 signal per CREATE and DROP.
T3: Skip WAIT_GCP

Temporary tables don't need durability guarantees. When a SchemaTransaction contains only temporary table operations, clear m_wait_gcp_on_commit to skip the WAIT_GCP_REQ at transaction complete.

Impact: Saves up to ~2 seconds of latency.
T4: Skip Backup Mutex in DROP

Temporary tables cannot be part of backups. Skip the backup mutex acquisition in dropTable_prepare() for temporary tables.

Impact: Eliminates potential blocking wait during DROP.
T5: Simplify DBDIH Processing

DBDIH must remain in the flow (DBTC uses it for fragment routing), but its work can be greatly simplified:

  • Skip ZPACK_TABLE_INTO_PAGES — no disk persistence needed
  • Skip table file writes to disk
  • Skip ReplicaRecord allocation — no replicas for temp tables (single copy)
  • Simplify fragment allocation — default single fragment, local node only
  • Skip LCP queue management and log part tracking
Impact: Eliminates all disk I/O in DBDIH + reduces memory allocation. Major speedup.
T6: Parallelize DROP Block Notifications for Temp Tables

Since temp tables have no concurrent users from other sessions, the sequential ordering constraint (drain DBLQH before stopping DBTC) can be relaxed. Send PREP_DROP_TAB_REQ and DROP_TAB_REQ to all blocks in parallel.

Impact: Reduces DROP from ~9 sequential round-trips to ~2 parallel rounds.
T7: Lightweight Schema Transaction

For temporary tables, the full SchemaTransaction with multi-node FLUSH broadcasts is unnecessary. A lightweight path could:

  • Skip all three RT_FLUSH_* phases — no schema file writes needed (saves 3 broadcast rounds + disk I/O)
  • Skip commit mutex acquisition/release — no serialization with other DDL needed
  • Allocate table IDs from a reserved temp-table range (avoid schema file scan in getFreeObjId())
  • Potentially skip RT_START/RT_END for single-node temp tables
Impact: Reduces from 11 broadcast rounds to ~5 (START, PARSE, PREPARE, COMMIT, COMPLETE, END minus FLUSHes). Eliminates all schema file disk I/O during DDL.
T8: Session Isolation

Temp tables should be invisible to other NDB API sessions. Natural isolation from:

  • No SUMA notifications → other sessions don't learn via replication
  • Reserved table ID range → other sessions won't stumble on the ID
  • Filter temp tables from listTables() for non-owning sessions
  • Auto-drop all session temp tables on disconnect
Impact: Enables safe multi-session usage.
T9: Pre-allocation and Pooling

For very rapid create/drop cycles, pre-allocate resources:

  • Pre-allocate a pool of table IDs reserved for temp tables
  • Pre-allocate Fragrecord slots in DBLQH
  • "Template table" concept: define schema once, rapidly instantiate copies
Impact: Reduces allocation latency for rapid create/drop patterns.
