Schema Transaction Optimization

Reducing the 11 broadcast phases for temporary tables, eliminating the schema mutex, and merging phases for normal tables — a concrete design for RONDB-1034.

1. The Problem: 11 Phases & the Schema Mutex

Today, creating a table requires 11 SCHEMA_TRANS_IMPL_REQ broadcast rounds, each a full round-trip to every data node. For a 2-node cluster, that is 44 messages just for phase coordination, before counting the actual DDL work (fragment creation, etc.).

Current 11 phases:

 1. RT_START           Alloc SchemaTrans on all nodes
 2. RT_PARSE           Execute parse handler on all nodes
 3. RT_FLUSH_PREPARE   Write schema file before prepare
 4. RT_PREPARE         Execute prepare handler (heavy: DBLQH/DBDIH fragment creation)
 5. RT_FLUSH_COMMIT    Write schema file + acquire commit mutex (DIH_START_LCP_MUTEX)
 6. RT_COMMIT          Execute commit handler (activate in DBTC/DBSPJ/DBDIH/SUMA)
 7. RT_FLUSH_COMPLETE  Write schema file + release commit mutex
 8. RT_COMPLETE        Execute complete handler (usually no-op)
 9. WAIT_GCP           Wait for Global Checkpoint (~2 seconds worst case)
10. RT_END             Write schema file + release SchemaTrans
11. dict_lock_unlock   Release schema lock
Plus: dict_lock_trylock() at the start serializes all DDL. Two concurrent CREATE TABLE requests run sequentially, not in parallel.

The Schema Mutex Problem

The dict_lock (a SchemaTransLock) is acquired at the very start of beginSchemaTrans() and held until RT_END completes. It is:

  • Node-local to the DBDICT master (not a distributed lock)
  • Exclusive: only one schema transaction can run at a time
  • Implemented as a FIFO LockQueue — other DDL requests wait in line
  • Also blocks during node restart (NodeRestartLock is shared, but conflicts with SchemaTransLock)

For temporary tables, holding this lock for the entire transaction duration means:

  • Creating a temp table blocks all other DDL on the entire cluster
  • Rapid temp table create/drop cycles serialize, can't be concurrent
  • A slow temp table creation (e.g., many fragments) blocks unrelated DDL
Why does the lock exist? It protects two things:
  1. Table ID allocation: getFreeObjId() does a linear scan of the schema file to find an unused slot. Without the lock, two concurrent creates could claim the same ID.
  2. Schema file consistency: The schema file has OLD and NEW copies. Concurrent writes to both could corrupt state transitions used for crash recovery.
For temporary tables, neither concern applies if we allocate IDs from a reserved range and skip schema file writes entirely.

2. Phase-by-Phase Dependency Analysis

To reduce the 11 phases, we need to understand what each phase does, what it depends on, and whether it can be removed, merged with an adjacent phase, or simplified.

3. Table ID Allocation Without the Schema Mutex

The schema mutex exists primarily to protect getFreeObjId(), which does a linear scan of the schema file for an unused table ID. For temporary tables, we can bypass this entirely.

Current Mechanism

getFreeObjId() (Dbdict.cpp:2707-2724):

  for i = 0 to (noOfPages * 127):       // Linear scan of ALL schema file entries
    if newSchemaFile[i].state == SF_UNUSED:
      if !both || oldSchemaFile[i].state == SF_UNUSED:
        return i                          // First free slot
  return RNIL                             // No free IDs!

Problems:
  • O(n) scan time where n = total table capacity (up to 20,320)
  • Requires schema lock to prevent two callers finding the same free slot
  • Checks BOTH old and new schema file copies (for crash recovery safety)

Proposed: Reserved Range with Atomic Counter

Temp Table ID Allocation (no schema mutex needed):

  Configuration:
    c_tempTableIdBase  = c_noOfMetaTables - c_tempTableIdPoolSize
    c_tempTableIdPoolSize = 2048           // configurable
    c_nextTempTableId  = atomic counter    // starts at c_tempTableIdBase

  getTempTableId():
    loop:
      id = atomic_fetch_add(&c_nextTempTableId, 1)
      if id >= c_noOfMetaTables:
        c_nextTempTableId = c_tempTableIdBase  // wrap around
        continue
      entry = getTableEntry(id)
      if entry.state == SF_UNUSED && !tableRecordInUse(id):
        return id                           // O(1) in common case
    return RNIL                             // pool exhausted

Why this is safe without the schema lock:
  • Normal tables never allocate from the temp range (getFreeObjId stops before it)
  • Atomic counter ensures two concurrent temp creates get different IDs
  • No schema file entries written for temp tables, so old/new copy conflict impossible
  • The only shared state is the atomic counter itself
Alternative: Per-API-node ID pools. The master could pre-assign ranges of temp table IDs to each API node (e.g., node 100 gets IDs 16000-16255, node 101 gets 16256-16511). This eliminates even the atomic counter contention. The API node picks the next ID locally and sends it in the CREATE_TABLE_REQ. The master validates it falls in the correct range. This maps naturally to session isolation (each API node's temp tables are in its own range).
Impact on normal tables: getFreeObjId() can be modified to stop scanning before the reserved temp range: for i = 0; i < c_tempTableIdBase; i++. This actually speeds up normal table ID allocation too, since the search space shrinks.

4. Temporary Table Design: 3 Phases

By removing the schema mutex, all FLUSH phases, the commit mutex, WAIT_GCP, SUMA notifications, and merging PARSE with PREPARE, we can reduce temporary table creation to 3 broadcast phases:

Phase 1: RT_PARSE_PREPARE (Merged)

The key insight is that PARSE and PREPARE can be merged for temporary tables because:

  • No crash recovery needed: If a node crashes mid-PREPARE, temp table data is lost anyway. There is no need for the FLUSH_PREPARE checkpoint that enables rolling back a half-prepared table.
  • Parse errors are still detected: The merged handler runs parse first. If parse fails, it returns REF immediately without starting prepare work.
  • No schema file state transitions: Normal tables need SF_STARTED → SF_PREPARE for recovery. Temp tables skip schema file entirely.
RT_PARSE_PREPARE handler on each node:

  1. START work (inlined, no separate broadcast):
     Allocate local SchemaTrans, set m_isMaster/m_masterRef

  2. PARSE work:
     createTable_parse():
       • Allocate SchemaOp + CreateTableRec
       • seizeTableRecord(tempTableId)     // ID already allocated by master
       • handleTabInfoInit()               // populate metadata
       • Build KeyDescriptor
       • If parse fails: return REF immediately (no cleanup needed)

  3. PREPARE work (only if parse succeeded):
     createTable_prepare():
       • writeTableFile()                   SKIPPED (temp table)
       • CREATE_TAB_REQ → DBLQH → DBTUP    // create table structure
       • LQHADDATTREQ → DBLQH               // add attributes
       • DIADDTABREQ → DBDIH                 // simplified: no replicas, no disk pack
         • LQHFRAGREQ → DBLQH → DBACC + DBTUP  // create fragment
       • TAB_COMMITREQ → DBLQH               // local commit

  4. Reply:
     SCHEMA_TRANS_IMPL_CONF → master
Error handling in the merged phase: If parse succeeds but prepare fails (e.g., out of fragment records), the handler must clean up the parse artifacts before returning REF. This is createTable_abortPrepare() followed by createTable_abortParse(), both of which already exist.

Phase 2: RT_COMMIT

This phase remains because DBTC and DBSPJ need to be notified that the table exists before operations can be routed to it. However, it is simplified:

RT_COMMIT handler on each node:

  createTable_commit() (simplified for temp):
    • CONNECT_TABLE_DB_REQ              SKIPPED (not needed for temp)
    • TAB_COMMITREQ → DBDIH             // tabStatus = TS_ACTIVE
    • TAB_COMMITREQ → DBSPJ             // enabled = true
    • TAB_COMMITREQ → DBTC              // enabled = true
    • TC_SCHVERREQ → DBSPJ              SKIPPED (not needed for temp)
    • CREATE_TAB_CONF → SUMA            SKIPPED (no replication)
    • commit mutex                       SKIPPED (no LCP interaction)

  SCHEMA_TRANS_IMPL_CONF → master

Phase 3: RT_END

Minimal cleanup:

RT_END handler on each node:

  • Write schema file                  SKIPPED
  • WAIT_GCP                           SKIPPED
  • Release SchemaTrans object
  • SCHEMA_TRANS_IMPL_CONF → master

  Master:
    • dict_lock_unlock()                 SKIPPED (lock was never acquired)
    • SCHEMA_TRANS_END_CONF → NDB API

What About DROP for Temp Tables?

DROP follows the same 3-phase pattern:

Temp Table DROP: 3 phases

Phase 1: RT_PARSE_PREPARE
  Parse: validate table exists, check version
  Prepare: no backup mutex (temp tables can't be backed up)

Phase 2: RT_COMMIT
  PREP_DROP_TAB_REQ + DROP_TAB_REQ in parallel to all blocks:
    • DBLQH: drop fragments (ACC + TUP + TUX), release Fragrecords
    • DBSPJ: release TableRecord
    • DBTC: release TableRecord
    • DBDIH: release Fragmentstore, TabRecord
  All four blocks notified in parallel (no sequential ordering needed
  for temp tables since there are no concurrent users from other sessions)
  • SUMA notification                   SKIPPED

Phase 3: RT_END
  • unlinkDictObject(), releaseTableObject()
  • Release SchemaTrans
  • Schema file write                   SKIPPED
  • WAIT_GCP                            SKIPPED
Merging PREP_DROP and DROP_TAB into COMMIT: For temp tables, the PREP_DROP and DROP_TAB signals can be sent together in the COMMIT phase rather than using separate COMMIT and COMPLETE phases. The sequential ordering (DBLQH before DBTC) exists to let in-flight operations drain. For temp tables with no concurrent users, this is unnecessary — all blocks can be notified in parallel, and both prep-drop and drop can be combined into a single step per block.

5. Normal Table Optimization: 7 Phases

Even for normal (non-temporary) tables, we can reduce the 11 phases to 7 by merging adjacent phases that have no fundamental reason to be separate broadcasts:

Merge 1: START + PARSE → RT_START_PARSE

RT_START allocates a SchemaTrans on each node. RT_PARSE executes the parse handler. There is no reason these can't be a single broadcast: the parse handler can allocate the SchemaTrans as its first step.

What RT_START currently does on slaves (Dbdict.cpp:30312-30360): Allocate SchemaTrans, set m_isMaster=false, set m_masterRef, set state TS_STARTED. This is ~10 lines of code. There is no reason this must be a separate network round-trip before PARSE.

Implementation: Add a new request type RT_START_PARSE that first runs slave_run_start() then immediately runs slave_run_parse(). The master sends a single broadcast instead of two. On error during parse, slave_run_start() cleanup is trivial (just release the SchemaTrans).

Merge 2: FLUSH_COMMIT + COMMIT → RT_FLUSH_COMMIT_AND_COMMIT

Currently these are two separate broadcasts. RT_FLUSH_COMMIT writes the schema file and acquires the commit mutex, then RT_COMMIT runs the commit handler. These can be merged because:

  • The schema file write in FLUSH_COMMIT is a prerequisite for COMMIT (crash recovery needs to know prepare succeeded before commit begins). But the write happens locally on each node, not as a distributed operation.
  • After the local write completes, the node can immediately run the commit handler.
  • The master just needs to know all nodes completed both steps, which a single CONF achieves.

Implementation: The merged handler writes the schema file (if m_flush_commit is set), acquires the commit mutex, then executes the operation's commit callback, then sends CONF. The master gets one round-trip instead of two.

Merge 3: FLUSH_COMPLETE + COMPLETE → RT_FLUSH_COMPLETE_AND_COMPLETE

Same reasoning as Merge 2. RT_FLUSH_COMPLETE writes the schema file and releases the commit mutex, then RT_COMPLETE runs the (usually no-op) complete handler. The local schema file write can be followed immediately by the complete handler in a single round.

Merge 4: Move WAIT_GCP before RT_END

WAIT_GCP is already not a broadcast — it's a signal from the master to its local DBDIH. It just needs to complete before RT_END releases the transaction. This is already the case today; we just list it as a distinct step because it adds latency. No merging needed, but it's worth noting that it does not add a broadcast round.

Why FLUSH_PREPARE can't be merged with PREPARE: The FLUSH_PREPARE schema file write records that a transaction has started. If a node crashes after PREPARE allocates resources (fragments, etc.) but before the schema file records this, crash recovery won't know to clean up those resources. The schema file write must complete on all nodes before any node begins PREPARE work. This is a fundamental safety requirement for normal tables. (Temp tables bypass this because lost resources are acceptable.)

7. Implementation Strategy

Step 1: Table ID Reservation (prerequisite)

  • Add config parameter MaxNoOfTempTables (default 2048)
  • Compute c_tempTableIdBase = c_noOfMetaTables - MaxNoOfTempTables
  • Add atomic counter c_nextTempTableId initialized to c_tempTableIdBase
  • Modify getFreeObjId() to stop scanning before c_tempTableIdBase
  • Add getTempTableId() using the atomic counter

Step 2: Add RT_PARSE_PREPARE request type

  • Add RT_PARSE_PREPARE = 0xb to SchemaTransImplReq
  • Add handler in execSCHEMA_TRANS_IMPL_REQ that calls slave_run_start(), then slave_run_parse(), then createTable_prepare()
  • Master's trans_prepare_start(): detect temp table, skip FLUSH_PREPARE and send RT_PARSE_PREPARE directly

Step 3: Temp table fast path in DBDICT

  • In execCREATE_TABLE_REQ: detect TableTemporaryFlag, allocate temp ID, skip beginSchemaTrans() / schema lock
  • Send RT_PARSE_PREPARE → RT_COMMIT → RT_END (3 rounds)
  • In commit handler: skip SUMA, skip TC_SCHVERREQ, skip CONNECT_TABLE_DB_REQ
  • In end handler: skip schema file write, skip WAIT_GCP

Step 4: Temp table fast path for DROP

  • Same 3-phase pattern: RT_PARSE_PREPARE → RT_COMMIT → RT_END
  • In commit: parallel PREP_DROP + DROP_TAB to all blocks simultaneously
  • In end: release DBDICT records, return temp table ID to pool

Step 5: Normal table merges (separate work item)

  • Add RT_START_PARSE request type
  • Add RT_FLUSH_COMMIT_AND_COMMIT merged handler
  • Add RT_FLUSH_COMPLETE_AND_COMPLETE merged handler
  • Update master state machine to use merged phases
  • Keep old request types for backward compatibility during rolling upgrades
Rolling upgrade compatibility: During a rolling upgrade, some nodes may understand the new merged request types while others don't. The master must check ndbd_support_merged_schema_phases(nodeVersion) before using merged types. If any node doesn't support them, fall back to the current 11-phase protocol. This is the standard NDB pattern for protocol evolution (see ndb_version.h.in).

8. Risks & Mitigations

RiskSeverityMitigation
Concurrent temp table creates race on table ID Medium Atomic counter ensures unique IDs. Validate with tableRecordInUse(id) check after increment. Retry on collision (wrap-around case).
Node crash during temp table PARSE_PREPARE leaves orphaned resources Medium At node restart, scan for table IDs in temp range and drop any that exist (temp tables are not expected to survive restarts). Add cleanup in execNDB_STTOR().
Parse error during merged PARSE_PREPARE requires aborting prepare artifacts Low The merged handler runs parse first. Only proceeds to prepare if parse succeeds. If parse fails, no prepare artifacts exist. If prepare fails after parse succeeded, call existing abortPrepare() + abortParse().
Merged FLUSH+COMMIT for normal tables: crash between flush write and commit handler Low If a node crashes after writing schema file but before running commit handler, crash recovery sees SF_PREPARE state and rolls forward (same as today). The commit handler is idempotent: running it twice is safe because TAB_COMMITREQ to DBTC/DBSPJ is idempotent.
Rolling upgrade: mixed cluster with old/new nodes Medium Version-gate all new request types. Master checks minimum node version before using merged phases. Fall back to 11-phase protocol if any node is old version.
Temp table ID pool exhaustion Low Return IDs to pool on DROP. If pool exhausted, return SchemaTransBeginRef::TooManySchemaOps error. Pool size is configurable.
API node disconnect with active temp tables Medium Track temp table ownership in DBDICT (API node → set of temp table IDs). On API node failure (execNODE_FAILREP() for API nodes), auto-drop all owned temp tables. This reuses the existing node failure handling framework.
Summary of improvements:
  • Temporary tables: 11 → 3 broadcast rounds, zero disk I/O, no schema mutex, no GCP wait. Estimated ~4-5x faster CREATE/DROP.
  • Normal tables: 11 → 7 broadcast rounds. Estimated ~25-35% faster CREATE/DROP (varies with network latency).
  • Both: No degradation in crash safety, recovery, or correctness. All optimizations are backward-compatible via version gating.
