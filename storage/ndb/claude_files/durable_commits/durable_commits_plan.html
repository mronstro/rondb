Durable commits across a cluster restart

Today a cluster restart brings the database back to the last GCI saved by the global checkpoint, so commits acknowledged in the last GCP interval can be lost. This plan makes every acknowledged commit survive a crash of all data nodes, power loss included, by putting the REDO log on persistent memory and logging one more record per operation.

1The conclusion

The review settled on these eight points. The rest of the page explains them.

  1. A config variable turns on disk durable commits. It is activated online at a chosen GCI and can only be turned off by a cluster restart.
  2. A config variable makes the REDO log use memory-mapped files. Durable commits need it, on persistent memory; otherwise the node refuses to start.
  3. A new COMPLETE record carrying the transaction id is written to the REDO log. The COMMIT record also gets the transaction id.
  4. Both the COMMIT and the COMPLETE record are persisted when written.
  5. Row locks are held until the COMPLETE record is persistent.
  6. Node restarts are not affected.
  7. A cluster restart first runs the normal recovery to the GCI that the global checkpoint made durable.
  8. A second phase then recovers the last GCI, which mixes committed and aborted transactions. A hash table keyed by transaction id queues the COMMIT records; a COMPLETE record executes them. Transactions left without a COMPLETE are resolved by asking the other REDO log parts.

What it costs. On the target hardware, CXL 2.0 persistent memory, a persist takes about 0.2–2 µs, so there is no fsync and no group commit. Each replica persists twice per write operation, and with two replicas the linear commit chain has four persists in series, 0.8–8 µs per transaction. The rest is message latency: the primary holds its row locks one round longer, and tables without READ_BACKUP get their ack one round later.

2Configuration and activation

  • Memory-mapped REDO. Each REDO log part becomes a memory-mapped file in a new format with a checksum on every record. A node switches to it with an initial node restart, so a cluster switches by rolling initial node restarts.
  • Persistent memory. The whole REDO log lives in PMEM: files on an ext4 or xfs file system mounted with -o dax, mapped once at start with MAP_SYNC and prefaulted. If MAP_SYNC fails the file is not on DAX, and the node refuses to start in PMEM mode, with or without durable commits. Hidden test modes run PMEM mode on emulated memory, or on any file (macOS, CI), without durability. Until PMEM hardware is available everything runs this way on normal DRAM, release builds and durable commits included; a test mode changes only the map flags and the start checks, so the persist code is the production code.
  • Writing. Records are built in DRAM log pages as today. At each persist point the new bytes are padded with a FILLER to the next 64-byte boundary, copied to PMEM with non-temporal stores and fenced. The same code serves ADR, eADR and CXL memory. Without durable commits the log is persisted at GCP save, at mbyte and file switches and when a page fills, which keeps today's durability.
  • Placement. Each log part's files sit on the persistent memory closest to the LDM thread that owns the part.
  • Refused in the first version: an encrypted file system, and Diskless. When an operation cannot be logged it aborts, as today; PMEM mode has no REDO log buffer to queue it in.
  • Online activation. When every node runs memory-mapped REDO, the DIH master picks an activation GCI g, sends it with the GCP protocol and writes it to the sysfile. Every transaction with GCI ≥ g uses the durable protocol.
  • Turning it off takes a cluster restart. That restart still recovers the durable tail, because the mode recorded in the sysfile governs the tail.
  • Testing without PMEM hardware. The Linux memmap= kernel parameter creates a RAM-backed /dev/pmem device that passes the DAX check. Data survives a process crash but not a reboot, which is enough for MTR and autotest.

3The commit protocol

The message rounds stay as they are. What changes is what each replica writes, and when it lets go of the row. The figure shows the linear commit of one operation with a primary P and a backup B.

TC sends COMPLETE only after every COMMITTED. So a COMPLETE record anywhere means every live replica of every operation has a persistent COMMIT record pointing back to its PREPARE. A change that was visible or acknowledged has a COMPLETE record. If no COMPLETE record exists, nobody saw the transaction and aborting it is safe.

Survival rule

A transaction survives the cluster restart if a COMPLETE record for it is found in some starting REDO log part. In a partial restart, a count fallback also applies (§7).

Here t_p is the prepare chain, t_c one hop and R the number of replicas; each replica also adds its persist time, 0.2–2 µs per barrier on CXL 2.0 persistent memory. A record is always persisted while its COMMIT or COMPLETE signal is handled, before the next COMMIT, COMMITTED, COMPLETE or COMPLETED is sent. A hot row's throughput limit, about one over the hold time, drops accordingly. Detached triggers, SUMA, the binlog and backup logging see the change one round later on the primary.

4REDO records

A PREPARE record holds the after-image of the row but no transaction id, table or GCI. Recovery can only reach it through the backward reference in a COMMIT record, and a PREPARE can be gigabytes back in the log. So recovery is driven by COMMIT records, as today, and a PREPARE without a COMMIT is never applied and never searched for.

On persistent memory the log keeps its geometry: files, 1 MB mbytes, 32 KB pages with a header on each page, and today's head and tail search. What changes is the unit of writing. A persist covers 64-byte units, so every record carries its own checksum and every page header is written once and never updated.

5Cluster restart

Phase 1: normal recovery to R_gcp

LCP restore, disk-data UNDO, and replay of the COMMIT records with GCI ≤ R_gcp run as today. Three things are no longer done for the durable tail: rewriting COMMIT records above R_gcp as invalid, moving the log head to the COMPLETED_GCI record of R_gcp, and the phase-4 invalidation. Nothing in the log is touched before phase 2 has decided.

Phase 2: the tail

The tail is normally the last GCI. It also holds the GCI before it if the crash came while that GCI's GCP save was still running. Each REDO log part of each starting node runs three steps. Step A runs inside the normal REDO execution scan, so phase 1 and phase 2 read the log in a single pass: COMMITs with GCI ≤ R_gcp are executed as today and the others go to the hash table. Step through phase 2 below on an example log part.

Step A: first scan

RecordAction
COMMITAppend a reference to the FIFO queue of its transaction id.
COMPLETE, entry foundExecute the queued COMMITs in log order through their backward references, then remove the entry.
COMPLETE, no entryIgnore. Another operation's COMPLETE already executed the transaction, or its GCI is ≤ R_gcp.
ABORTRemove the entry. Its COMMITs are invalidated in step C.

No COMMIT of a transaction can follow its COMPLETE in the same log part, because COMPLETE is only sent after every COMMITTED. What is left in the table at the end is the log part's in-doubt set.

Step B: exchange between log parts

There is no coordinator. Every log part sends its in-doubt set to every other part, as transaction id and the number of COMMIT records it holds. The COMMIT records stay local. Each part then scans its tail a second time for COMPLETE and ABORT records of the transactions it was sent, and answers the parts that asked. Three new data-node-only signals carry this, SR_TAIL_INDOUBT_REP, SR_TAIL_HIT_REP and SR_TAIL_DONE_REP, aggregated per node in the DBLQH proxy. The done signal also carries the part's highest executed GCI, so every part computes the same new restorable GCI.

Step C: verdicts

Condition, once "done" has come from every partVerdict
"T complete" receivedCommit: execute the queued COMMITs in log order.
Otherwise the counts pass the node-group rule (§7) and no "T aborted" was receivedCommit, the same way.
OtherwiseAbort: mark the transaction's COMMIT records invalidated, one atomic flag store each. The flag sits outside the CRC, so the records stay valid and the log is not cut there.

The hash table is then freed. A restart that crashes partway through is repeatable: nothing in the log changes before every part is done, and after that only the COMMITs of aborted transactions are rewritten, which a rerun aborts again.

Phase 3: raise the restorable GCI

  • Set the restorable GCI to the highest GCI applied in phase 2, durably, before the restart LCP and the first new GCP. The sysfile, DIH, DBLQH, Backup, NDBCNTR and the DIH replica intervals must all see it.
  • Keep the LCP-restore bound at R_gcp.
  • Put the new log head after the old tail and write an SR-head record, so a repeated restart finds the same state. New GCIs start above the new restorable GCI.

6Why log order is enough

Each log part executes the surviving transactions in its own log order, with no ordering across fragments or transactions, and every row still ends as a serial execution of the survivors would leave it. The cost is linear.

  • After-images. REDO records hold the values written. Interpreted updates are logged as their resulting ATTRINFO. Applying a record depends only on its own row.
  • Locks are held to the COMPLETE record. On each replica a writer keeps its row lock until its COMPLETE record for that operation is persistent, or until its ABORT record. The next writer of the row logs its PREPARE, COMMIT and COMPLETE only after that.
  • GCI order. If T2 read or overwrote T1's write, GCI(T2) ≥ GCI(T1), so phase 1 followed by phase 2 keeps each row's order.
  • FIFO within a transaction. Several operations of one transaction on the same row keep their order.

Take T1 before T2 on row r. T1's COMPLETE for r comes before T2's COMMIT for r. T1 is executed at its first COMPLETE in this log part, T2 at its own COMPLETE or in step C, so T1 runs first. If T1 has no COMPLETE in this log part, it still held the lock on r at the crash, and nothing follows it on r. In the example above, T11 writes row a at record 13, after T7's COMPLETE of row a at record 8.

Dependencies are kept. If T2 read T1's write, the write was visible, so T1 has a COMPLETE record and survives. Routing the tail through TCs instead would throw away the order the log already holds and would re-fire triggers and take locks.

7Node failures

A node failure in the tail GCI (D3)

Rule F covers transactions in flight when a node fails. Transactions that start after the failure run on the surviving replica alone. If the cluster then crashes before that GCI is saved by GCP, every sysfile still shows the failed node as restorable, and its replicas would miss those transactions. So the failure must be persisted before anything can be committed without the failed node.

Stale nodes

A starting node X is stale if some starting node recorded X's failure in a GCI above R_gcp: X failed after the last GCP save, the cluster ran on without it, and no sysfile shows it. A stale node takes no part in the cluster restart, neither phase 1 nor phase 2. It is restarted by a node restart once the other nodes have recovered, the same way NDBCNTR already treats a node that cannot be restored from its own REDO log (m_withLogNotRestorable, NdbcntrMain.cpp:2730-2743). The node-failure records therefore travel with each node's start request, before the master fixes the node sets. A node is also stale if its PMEM device reports an unsafe shutdown since the last start: its REDO is still readable up to its valid end, since the checksums cut off failed last writes, but writes already acknowledged as persistent may be missing. Recovery needs at least one non-stale node in each node group.

The proof of commit is on a missing node (D5)

With linear complete, the backup writes its COMPLETE and makes the row visible before the primary gets COMPLETE. If the backup's node does not come back, no starting log part may have a COMPLETE for the transaction, although someone may have seen it. The fallback uses the counts from step B.

  • Every node of a node group holds a replica of the same fragments and writes one COMMIT record per operation on them. A node's count is therefore the number of the transaction's operations in its node group that it has COMMIT records for.
  • Node-group rule: within each node group every node taking part in the restart reports the same count, and the counts of the node groups add up to opCount. Then every operation has a COMMIT on every replica in the restart, and the transaction commits.
  • This always holds once any COMPLETE was written. A transaction with every COMMIT and no COMPLETE may correctly go either way, since nobody saw it. A "T aborted" from step B vetoes the rule, so it never revives a transaction aborted by rule F.

Open for the later steps (found while planning the implementation; proposals in implementation_plan.md):

  • Dirty writes. A dirty write logs PREPARE, COMMIT and COMPLETE together and takes its GCI from DBLQH, so its COMPLETE record would wrongly tell the restart that the whole transaction is complete. Either flag such records or turn dirty writes into normal writes in durable mode.
  • Read locks. Released at COMMIT, or held to COMPLETE like write locks.
  • Takeover race. A COMPLETE sent by the failed TC may be executed after the takeover TC has collected the operation states, so its "was any COMPLETE sent?" decision must be checked in the code and in the TLA+ model.

9Risks and work plan

Risks

  • Persist barriers. Several LDMs can share a log part, so a barrier must cover the part's whole unpersisted range. A missing barrier is a silent bug; a debug check and power-loss emulation that keeps only what was written up to the last barrier guard against it.
  • Moving the primary's local commit touches the hottest commit code: the queued-log path, tupcommit_conf, the parallel and takeover paths.
  • Longer lock hold on the primary. Measure hot-row throughput and deadlock-timeout aborts.
  • Rule F needs an abort path from the committed state in DBLQH, and the takeover TC must know whether any COMPLETE was sent.
  • opCount must be right for trigger-generated operations, IgnoreError aborts and takeover.
  • Transaction id reuse. The API's counter starts at 0 again when the API process restarts. A failed API node id is therefore not taken into use again until the GCI in which it failed has been saved by GCP, enforced in QMGR's API_REGREQ handling.
  • Activation boundary. Phase 2 applies only to GCI ≥ g, and only when R_gcp ≥ g−1.

10First step: the REDO log on persistent memory

The first implementation step puts the REDO log on persistent memory with today's durability: a GCI is durable once the global checkpoint has saved it. The durable-commit protocol and restart phase 2 build on it. The full design is pmem_redo_design.md; everything below is settled.

Finding the end of the log at restart

Between two barriers the 64-byte lines of a copy can reach persistent memory in any order. A crash can therefore leave a valid record after an invalid one.

Implementation steps

Each step ends in something that can be tested on its own. After S7 the REDO log runs on persistent memory at today's durability.

S1CRC32C and PMEM helpers: map, prefault, non-temporal copy, fences, power-loss emulation.
S2 · parallelConfig: RedoLogMode, a path per NUMA node, start-up refusals, ndbinfo.
S3NDBFS maps the files with MAP_SYNC; full initialisation at initial start.
S4Record writers: header and CRC, write-once page header, FILLER, new COMMIT and ABORT.
S5Write path: the persist primitive, copy-out, GCP save, mbyte and file switch.
S6Recovery: end of log, slots, zeroing, new record types, node restart, redoLogReader.
S7Power-loss tests: torn-copy error insert, emulation, acknowledged-write checker.

Tests on emulated persistent memory (memmap=, or QEMU's emulated CXL memory device) prove the format, the write path and the recovery logic, and survive kill -9. They can never catch a missing barrier; only the power-loss emulation of S1 and S7 can. Performance needs real CXL modules.
